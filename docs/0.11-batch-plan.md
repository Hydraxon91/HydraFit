## Accepted product boundaries

- Equipment identity means exercise + equipment profile + station/implement +
  load basis, never inferred machine/cable/barbell conversion factors. Preserve
  history; do not guess ambiguous old station attribution.
- Station/grid setup is optional in Equipment settings. Show unknown identity
  explicitly; do not require onboarding to log a workout.
- EQ-03 onboarding inventory capture and LT-09 temporary machine exclusions stay
  outside these batches. They remain separately gated, not canceled.
- Distance starts with manual distance and distance-plus-load records for carries,
  with comparable history/charts and portability. Automatic carry prescription
  and progression are excluded from this initial scope.
- Cardio starts with manual offline activity logging, history/charts and
  portability. GPS, wearables, calorie estimates and automatic cardio programming
  are excluded. Ownership and exact activity/measurement scope remain open.
- Already-delivered timed sets, timed prescriptions, accepted-plan slot durations
  and persisted timed preparation are reused, not reimplemented.

### Clusters — accepted behaviour (0.11.3)

| Decision | Accepted behaviour |
| --- | --- |
| Supported input | Rep-based external-load cluster work, manually authored. No automatic cluster or drop-set generation. |
| Why not wider | Timed, distance and force measures already have their own exclusive contracts; extending clusters to them needs separate evidence. |
| Structure | One cluster parent with ordered segments. Each segment keeps its own load, reps and optional RIR. |
| Prescription | Explicit segment targets and rest settings authored by the user. No invented drop percentage, segment count or rest default. |
| Completion | One parent occupies one prescribed set position. Segments never inflate the ordinary set counter. |
| Partial work | Early termination records a partial parent. Saved segments survive interruption and resume without duplication. |
| Rest | Prescribed rest drives guidance only; it is not reported as measured rest unless actual timing is recorded. |
| Volume | Descriptive sum of segment external load × reps across eligible segments. Never presented as ordinary-set equivalence. |
| Records and progression | Excluded from ordinary strength records, estimated 1RM and automatic success/miss progression. Segment history shown separately. |
| Fatigue | Excluded from modelled fatigue and planner volume credits, with the limitation visible rather than silently presenting a complete estimate. |
| Coverage | The trained muscles are recognised so last-trained stays truthful, but cluster counts are displayed separately from ordinary working-set counts. |
| Edit and delete | Segment edit recomputes the parent summary; segment deletion preserves remaining history; whole-parent deletion is a separate explicit action. |
| Nesting | No cluster inside a superset initially. Ordering and recovery interactions need their own decision. |
| Portability | Structure, segment values and rest survive backup, replace/merge restore and supported interchange. |

### Cardio — accepted behaviour (0.11.4)

| Decision | Accepted behaviour |
| --- | --- |
| Record shape | A separate cardio activity record, never a resistance set. The exclusive-measurement rule is not widened. |
| Measures | Start time and duration required; distance and note optional. Duration and distance may coexist. |
| Activities | Walking, running, cycling, rowing and Other. No wider taxonomy yet. |
| Relationship | Standalone activities that may overlap a resistance workout in time but never join its completion, fatigue or session segmentation. |
| Ownership | A dedicated cardio feature module in principle. The exact module name, registration and navigation entry are proposed in the execution contract and remain an individually gated module-graph change. |
| History and charts | Distinguished history plus duration and distance totals by activity type. Pace or speed only where duration and distance both exist, computed from matching totals rather than averaged per-activity values. |
| Aggregation | No combined cardio score, no cardio-to-strength conversion. |
| Corrections | Edits and deletions update history and chart totals; a repeated merge must not duplicate activities. |
| Portability | Backup, replace/merge restore and analysis export carry activities. |
| Exclusions | No calories, GPS, wearables, cardio prescriptions, strength records, muscle-fatigue conversion or readiness adjustment. |

### Evidence gathered (read-only)

- **Exclusive measurement is enforced, not advisory.**
  `core/domain/src/commonMain/kotlin/com/hydrafit/app/core/domain/workout/WorkoutSet.kt:107`
  requires exactly one of reps, seconds, metres or newtons, and every write path
  calls it (`LogWorkoutSetUseCase.kt:33`). A duration-plus-distance cardio shape
  therefore cannot reuse `WorkoutSet`, which is why cardio needs its own record.
- **Completion counts recorded set rows per slot.**
  `WorkoutSummary.kt:82` defines `recordedSets` as `performedSets.size`, and
  `WorkoutSummary.kt:222` derives `remainingSets` from that against `entry.sets`.
  A cluster parent that stays **one** recorded set keeps completion, "extra sets"
  and the post-workout summary unchanged; segment rows in a separate table cannot
  inflate the counter.
- **A parent row can stay an ordinary set.** Because segment values live in a child
  table, the parent keeps a valid single measurement, so existing consumers keep
  working and only the consumers being excluded need an explicit check.
- **Fatigue reads sets by measure and capability.**
  `SqlDelightWorkoutLogRepository.kt:150` drops timed rows and maps the rest;
  `ExerciseProgressCalculator.kt:42` already early-returns for timed, distance and
  force rows. Cluster segments need the same explicit treatment rather than being
  silently summed.
- **Coverage is an independent consumer.**
  `SqlDelightTrainingCoverageRepository.kt:15` derives coverage from recorded
  involvements only, so excluding clusters from fatigue does not by itself settle
  coverage; the accepted decision addresses it separately.
- **Superset precedent is reusable.** `RoutineTemplate.kt:57`,
  `WorkoutSchedule.kt:93`/`:152` and additive `59.sqm` show the established pattern
  for a nullable structure carried on the same four prescription kinds, with
  `SupersetJson` decoding and a validator rule. Clusters should follow that shape.
- **Ordered targets show the same additive pattern.** `setTargets` arrived as
  additive `58.sqm` on the same four tables, decoded on read, which is the closest
  precedent for per-segment prescriptions.
- **Portability baselines.** `BACKUP_FORMAT_VERSION = 27`
  (`BackupModels.kt:10`) and the last migration is `62.sqm`, so the next additive
  schema step is `63.sqm` and the next backup format is `28`. `BackupModels.kt:117`
  enumerates the payload sections a new record type must join, and
  `BackupMergePolicy.kt:18` inserts only sessions/sets absent locally, which is
  where activity deduplication must be defined.
- **Analysis export is a separate writer.** `WorkoutHistoryCsvWriter.kt:56` owns the
  CSV column set, so cardio needs a deliberate column decision rather than reusing
  set columns.
- **Navigation precedent favours a pushed destination.**
  `App.kt:96` registers six top-level destinations, and `App.kt:127` documents
  Progress as a standalone pushed route that the shell owns so the Logger can offer
  it without importing the feature. Cardio should follow that pattern instead of
  adding a seventh `AppTab`.
- **Emulator availability.** `emulator-5554` is running an older debug build
  (`0.7.6-dev-688a7f3f-dirty`); acceptance needs a fresh debug install. Thirty-four
  `.maestro` flows exist, including the 0.11.x measurement journeys that can be
  reused as regression coverage.
